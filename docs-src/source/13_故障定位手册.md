# 安装与运行故障排查

本章介绍 AscendMOEA 安装、设备配置、性能测试和批量实验中的常见问题。排查前请保留失败任务的配置、完整日志和输入数据，并在单独目录中复现问题，避免覆盖已有实验结果。

## 建议的排查顺序

建议依次检查以下四个方面：

1. **软件环境**：确认 Python 环境、软件包版本和导入路径正确。
2. **计算设备**：确认 CPU 或 NPU 可用，且程序实际运行在指定设备上。
3. **数值计算**：检查数据类型、张量形状、约束定义以及 NaN、Inf 等异常值。
4. **算法流程**：检查评价次数、终止条件、种群更新和监控逻辑。

每完成一项检查，都应记录检查命令及其输出，便于比较修改前后的结果。

## 安装和导入问题

### 无法导入 `ascendmoea`

出现 `ModuleNotFoundError: No module named 'ascendmoea'` 时，通常是当前 Python 环境中尚未安装 AscendMOEA，或者运行程序所用的 Python 与安装软件包时使用的 Python 不一致。

执行以下命令检查环境：

```bash
which python
python -m pip show AscendMOEA
python -c "import ascendmoea; print(ascendmoea.__file__)"
```

如果 `pip show` 没有输出，请在项目根目录重新安装：

```bash
python -m pip install .
```

如果使用虚拟环境，请先激活虚拟环境，再执行安装和运行命令。

### 找不到 MAT 数据文件

部分实际问题需要读取随软件包发布的 MAT 数据文件。如果源码目录中可以运行，但安装后提示数据文件不存在，请检查以下内容：

- 安装包中是否包含 `ascendmoea/vendor/**/*.mat`；
- `pyproject.toml` 中是否正确声明了软件包数据；
- 程序是否通过 Python 软件包资源接口读取数据，而不是依赖当前工作目录；
- 当前安装的软件包是否为最新构建版本。

修改软件包数据配置后，应重新构建并安装软件包，再进行验证。

## NPU 无法使用

首先检查设备状态：

```bash
npu-smi info
python -c "import torch, torch_npu; print(torch.npu.is_available())"
```

如果 `npu-smi info` 无法正常显示设备，请检查 NPU 驱动和固件。如果设备状态正常，但 `torch.npu.is_available()` 返回 `False`，请依次检查：

1. CANN 是否正确安装；
2. CANN 环境变量是否已经加载；
3. PyTorch 与 `torch_npu` 的版本是否匹配；
4. Python 版本是否在当前软件栈的支持范围内；
5. 当前用户是否具有访问 NPU 设备的权限。

不要使用普通 CPU 版或 CUDA 版 PyTorch 覆盖与 `torch_npu` 配套的 PyTorch。升级组件前，应先查阅当前 CANN 与 `torch_npu` 的版本兼容说明。

## CPU 任务占用 NPU 0

CPU 任务出现在 `npu-smi` 进程列表中，通常是 PyTorch 自动加载设备后端所致。请在首次导入 PyTorch 之前设置：

```bash
export TORCH_DEVICE_BACKEND_AUTOLOAD=0
export ASCENDMOEA_DEVICE=cpu
```

同时确认程序显式指定了 CPU：

```python
result = optimize(algorithm, problem, device="cpu", seed=42)
```

修改后应重新启动 Python 进程。已经完成的性能测试如果包含 NPU 后端初始化时间，应重新运行，以免影响时间和内存统计。

## NPU 运行速度低于 8 线程 CPU

NPU 并不一定在所有规模下都快于 CPU。小种群、较低评价预算或频繁的主机与设备通信，都可能使设备调度开销超过并行计算收益。

建议按以下顺序检查：

1. 确认算法、问题和主要张量实际位于目标 NPU；
2. 确认 CPU 与 NPU 使用相同的种群规模和最大评价次数；
3. 完成一次预热，避免将首次编译时间计入稳定运行时间；
4. 在计时开始和结束时执行 NPU 同步；
5. 检查循环中是否频繁调用 `.item()`、`.cpu()` 或 `.numpy()`；
6. 检查目标函数和算法算子是否按种群批量计算；
7. 避免在循环中创建 CPU 张量后再复制到 NPU；
8. 确认同一张 NPU 上没有其他任务争用计算和显存资源；
9. 使用 `npu-smi` 检查设备利用率、显存占用和功耗；
10. 使用性能分析工具或分段计时确定耗时最多的步骤。

找到瓶颈后，再根据具体情况采用批量计算、减少设备同步、复用常量张量或增大任务规模等方法。仅增加最大评价次数不会改善单次迭代中的低效计算。

## 内存占用异常

### 多进程 RSS 总和过大

RSS 会在多个进程中重复统计共享库和共享内存，因此不能直接将所有进程的 RSS 相加作为实际物理内存占用。多进程实验应同时查看 PSS，并区分以下进程：

- 主进程；
- 并行工作进程；
- CANN 编译或运行时进程；
- 日志与监控进程。

如果内存持续增长，请分别记录各类进程的 PSS、RSS 和进程数量，以确定增长来源。

### NPU 显存持续增长

重点检查以下内容：

- 监控器是否长期保存了每一代的 NPU 张量；
- 算法缓存是否在每一代追加数据但没有释放；
- Python 容器或回调函数是否仍然引用已经不用的张量；
- 是否为每次迭代重复创建形状相同的大型临时张量。

需要长期保存的种群数据应及时复制到 CPU，并采用逐代写入方式保存。不要在 NPU 上保留完整实验历史。

### 二次复杂度算子导致显存不足

支配关系矩阵、两两距离矩阵等算子的空间复杂度通常为 $O(N^2)$。种群规模增加时，显存占用会快速增长。

排查时应记录：

- 种群规模和张量形状；
- 数据类型；
- 输入张量与中间张量的数量；
- 峰值 NPU 显存；
- 发生内存不足时所执行的算子。

可以通过减少重复中间结果、分块计算或降低不必要的计算精度来控制显存占用。如果实验规模超过单卡容量，应明确记录失败条件，不应在未说明的情况下改变种群规模、选择规则或截断规则。

## 指标结果异常

| 现象 | 检查内容 |
|---|---|
| 指标为 NaN 或 Inf | 检查目标值、参考数据、归一化分母以及可行种群是否为空 |
| HV 为 0 | 检查参考点、最小化方向以及归一化后的解是否超出参考范围 |
| IGD 很大但前沿图形正常 | 检查目标列顺序、目标数量和参考前沿维数 |
| IGDX 明显异常 | 确认输入的是决策空间参考集，而不是目标空间参考前沿 |
| 可行率始终为 0 | 检查约束是否采用 `g(x) <= 0`，并确认等式约束容差合理 |

比较不同设备的指标时，还应检查 CPU 与 NPU 是否使用相同的数据类型和容差设置。

## 批量任务长时间没有进度

单个任务运行时间较长，并不一定表示程序停止运行。应综合检查：

- 进度文件的最后更新时间；
- 日志文件是否继续写入；
- 进程的 CPU 使用率和 I/O 活动；
- NPU 利用率和显存占用；
- 同类算法与问题的历史运行时间；
- 当前是否正在进行算子编译或高开销指标计算。

只有在任务超过预设超时时间，并且进度、日志、CPU、I/O 和 NPU 状态均无变化时，才能判定任务可能失去响应。终止任务前，应保存进程树、日志、设备状态和当前任务配置。

## 最小复现示例

提交故障报告前，请将问题缩减为能够稳定复现的最小任务。至少提供以下信息：

- 一个算法和一个问题；
- 固定的随机种子；
- 明确的 CPU 或 NPU 设备；
- 能够复现问题的最小种群规模和评价次数；
- AscendMOEA、Python、PyTorch、`torch_npu` 和 CANN 版本；
- 完整错误信息和运行命令。

问题修复后，仅重新运行受影响的实验任务，并保留原始失败记录以便核对。
